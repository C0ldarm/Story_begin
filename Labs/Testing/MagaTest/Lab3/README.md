# Лаба 2: Оптимізація пам'яті 

Коротше, зробив оптимізацію для другої лаби. Нижче порівняння двох версій.

## Що порівнював
- **V1 (стара)**: `WordFrequencyAnalyzer.java` — дефолтний код з репо на стрімах. Перейменував клас, бо `Main.java` з новим класом не збирався.
- **V2 (нова)**: `WordFrequencyOptimized.java` — переписана версія, щоб їла менше пам'яті.

## Що змінив у V2
1. Читаю файл шматками по 64 КБ через буфер, а не весь одразу через `readString()`.
2. Замість `split()` та `Stream` токенізую вручну, щоб не перевантажувати пам'ять об'єктами `String`.
3. Написав власну хеш-таблицю (слова в одному `byte[]`, частоти в `long[]`), викинув стандартний `HashMap`.
4. Топ-N шукаю через мін-купу, а не сортую взагалі всі слова.

*Вивід V2 такий самий, як і у V1 (перевіряв на `harry.txt` та інших тестах).*

Тестував на `harry.txt` (449 КБ). 15 запусків, взяв медіану:

| **Час внутрішній** | 168 мс | 16 мс | ~10x швидше |

| **Пікова RSS** | 59 МБ | 44 МБ | -15 МБ |

## Масштабування (великі тексти)

| Текст | Час (V1 → V2) | RSS (V1 → V2) | Мін. `-Xmx` (V1 → V2) |
| :--- | :--- | :--- | :--- |
| **1.1 млн слів (7 МБ)** | 581 мс → 57 мс | 213 МБ → 46 МБ | 96 МБ → <= 4 МБ |
| **8 млн слів (53 МБ)** | 2818 мс → 444 мс | 941 МБ → 52 МБ | 768 МБ → 8 МБ |

V1 вилітає по пам'яті на великих файлах, а V2 байдуже на розмір файлу — вона залежить тільки від кількості унікальних слів.
